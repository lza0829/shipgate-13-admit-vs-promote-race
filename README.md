# 发版闸（Shipgate）

骨架：发版申请入闸 → 环境晋升裁决 → 放行/回滚窗 → 发布结果对账

- 前端 http://127.0.0.1:6800
- API http://127.0.0.1:11800
- 数据库环境变量 `SHIPGATE_DB`（容器内默认 `/data/shipgate.db`）

```bash
docker compose up -d --build
```

## 入闸/晋升争用收口（全站唯一结局）

实现方敲定并贯彻的口径：**以入闸完成前拒绝晋升为准**。

发版单未到「已入闸」时，晋升整笔失败——不改环境、不写晋升事件、不动名册版本，
总览不假装跃迁；失败带「争用戳」（`CT-…`）落审计，且为暂时性失败，入闸完成后可重试。
结构上杜绝「待入闸却挂着晋升事件」「半截单态」「双回执拧花」。

收口机制：

1. **单写事务**：入闸/晋升/回滚各在一个 `BEGIN IMMEDIATE` 即时写事务内完成
   「读状态 → 条件流转 → 写全部落点（状态/事件/当前环境/名册/实例/审计）」，同成败、可重放，
   失败整笔撤到争用前。WAL 让总览/对账旁读不阻塞写口。
2. **三段式在途登记**：进程内每单发版单一把锁 + 持久化在途登记 `release_locks`（带 TTL，
   设置项 `在途锁TTL秒`）。登记在业务事务之前独立提交，故进程硬杀时僵锁真实残留，由后来者
   在 TTL 到期后接管并留审计；普通业务异常则主动释放登记。
3. **幂等重放**：写口支持 `Idempotency-Key` 头，同令牌同请求只执行一次、回放同一落账结局；
   同令牌异请求体直接 409。前端写请求默认带令牌，双击/重试自动收口。
4. **晋升事件序号**：`promote_events.seq`，单内从 1 连续、唯一索引兜底，事务回滚不留号。
5. **争用戳对齐**：发版单详情、总览在途、对账、审计同一戳可互查。

### 对账一致性核查（`GET /api/对账`）

- 待入闸不得挂晋升事件
- 晋升事件序号连续不重号
- 当前环境与末条晋升事件落点对齐（已入闸单落测）
- 名册版本跟齐当前环境
- 无超时僵锁（未过期的在途登记是合法瞬态不报，过期才提示待 TTL 接管）
- 总览在途口径一致（挂晋升事件的单不得停在待入闸；纯在途登记不在此列）
